# J5 CAN 시험 준비 / ESP 펌웨어 확인 141

2026-11-12 KST. 모터 전원은 사용자 보고상 OFF이며 계측한 값은 아니다. ESP 보드는 사용자 확인 ESP32-S3-RS485-CAN(U 없음), 리비전 미확인이다. 이번은 USB 펌웨어 확인과 오프라인 준비이며 실제 J5 CAN 조회·급전·이동·교정·flash 단계가 아니다.

## 준비 도구

기존 로컬 Python: `.dev/tools/esp-idf-local/tools/python_env/idf5.5_py3.12_env/Scripts/python.exe`. 새 설치 없이 pyserial3.5/esptool4.12.0을 사용한다. 저장소 루트에서 이 Python으로 `src/bench/j5_can141.py plan`을 실행하면 실제값 null·송신0인 준비 상태를 출력한다. `plan --candidate-id 1` 또는2는 후보 프레임만 보여주며 실제 주소 설정/조회/통신을 하지 않는다. J5≠CAN ID5다.

기존 `src/firmware/diagnostic/`는 physicalReadApproved=false/static_assert이고 Board::WaveshareCanU만 허용한다. 현 non-U 보드는 기존 경로에서 BLOCKED_BOARD_ENUM_MISMATCH다. 이번 도구는 이를 우회하거나 실제 CAN-U로 간주하지 않는다. 향후 보드별 지원 수리·독립 검토·새 실행 범위가 필요하다. 기존 펌웨어는 변경하지 않는다.

## USB 확인 순서

1. 사용자 보고상 모터 전원 OFF를 유지하고 J5를 받침으로 지지한다. USB만으로 드라이버·모터가 무동작이라는 증거를 얻은 것은 아니다.
2. `observe --motor-power-off --out outputs/esp-j5-can-prep-141/usb-observe`는 COM7 VID303A PID1001을 재확인한 뒤 8초 수신 스케줄/64KiB로 수신한다. 매 읽기 대기는 최대0.2초이며 마지막에는 잔여시간으로 줄인다. 실제 elapsed_s에는 OS·열기·닫기 지연이 포함되어 절대8초 종료를 뜻하지 않으며 실행자는 외부20초 프로세스 상한을 적용한다. DTR/RTS=false를 열기 전 지정하며 앱 바이트 write나 reset sequence를 호출하지 않는다. OS 제어선 glitch나 현재 앱의 CAN 활동까지0으로 보증하지 않는다. raw는 로컬 rx.bin, 상태는 capture.json. 침묵은 미식별이다. 출력 디렉터리가 이미 있으면 덮지 않고 실패한다.
3. 식별되지 않을 때만 esptool의 `--chip esp32s3 --port COM7 --baud 115200 --before usb_reset --after hard_reset --no-stub --connect-attempts 1 read_flash 0x8000 0x1000`으로 파티션 테이블을 별도 새 파일에 읽는다. 이 읽기는 USB ROM 요청과 ROM 진입/앱 복귀 리셋을 수반한다. 프로세스 외부 상한45초/세션최대2/재시도0이다.
4. `partition <로컬4KiB파일>` 검증이 성공하고 저장 앱이 정확히 하나일 때만 그 앱 주소의 첫0x1000바이트를 같은 read-only 플래그로 한 번 읽는다. 앱 주소를 기본0x10000으로 추측하지 않는다. `app <로컬4KiB파일>`은 저장 메타데이터만 판독한다. 현재 실행 앱·전체 이미지 해시·소스 동일성·동작 안전성의 인증은 아니다. 다중 앱/MD5 불일치/암호화/범위·형식 이상이면 중단한다.
5. 실패/timeout에는 앱 복귀나 ROM 잔류 상태를 확정하지 않는다. 추가 reset/복구/flash로 확장하지 않는다. 앱 재시작 후 자체 CAN 통신과 NVS 변경은 NOT_MONITORED다. 호스트 CAN 요청은0, 실제 J5 CAN 시험은 NOT_RUN이다.

read_flash 외 write_flash/erase/load_ram/보안·eFuse 설정 변경은 하지 않는다. NVS 영역이나 전체 flash는 읽지 않는다. 앱 헤더에 포함될 수 있는 식별 정보도 로컬에만 보관하고 MAC/USB serial 등은 사용자 전달 결과에서 생략한다. USB 접근 결과·오프라인 HOST·실제 모터 시험은 따로 기록한다.

## J5 전원 투입 전에 확인할 항목

| 항목 | 현재 상태 |
|---|---|
| 관절 / 통신 | J5 / CAN 사용자 확인 |
| ESP 제품 | ESP32-S3-RS485-CAN, U 없음 / 보드 리비전 미확인 |
| J5 드라이버 HW/FW, 실제 CAN ID/CanRate | 미확인 |
| 기존 진단의 기대값 |500kbit/s,TX15/RX16,CAN-U 전용 — 실제 설정값 아님 |
| 모터 정격 상전류·Ma / PSU V·입력 전류제한·퓨즈·전선 | 미확인. 서로 같은 전류로 간주하지 않음 |
| H→H / L→L / 전원V+·GND / 고정·받침·차단수단 | 실물 대조 대기 |
| 120Ω 점퍼 | MKS 단독 예시OFF와 일반 양끝120Ω 기준을 실제 구성에서 대조할 것. 사진 없이 어느 핀을 꽂을지 확정하지 않음 |
| 읽기 후보 |31 위치,32 속도,F1 운전상태,3A enable상태. 모두 조회이며 enable/이동 명령과 다름 |
| 실제 CAN·모터 구동 | NOT_RUN / hardware_approved=false |

서플라이 전류를 임의로 높이거나 CC를 토크 제한 대신 사용하지 않는다. READ 요청만 준비돼도 공장 앱/모터의 전원 투입 동작은 별도 확인해야 한다. 그리퍼 STS3215 TTL과 J6는 이번 한축 시험에서 제외한다.
