# 정지 시간 수정과 펌웨어 준비 1차

2026-10-22 · 신선 계보 ST1 · **HOST_CORE_READY** — L2 R1 PASS, C++호스트검증완료, L4수정재확인완료. 상세처분 `.dev/firmware-core-evidence/disposition.md`. 사용자: “정지 확인 시간 문제부터 수정하고 펌웨어 준비 계속 진행”

## 권위와 범위

사용자 후속 지시로 지난 검토의 R3-R2-1을 다시 다룬다. 동결된004/005/006과 이전 검토 해시는 보존한다. **정지 시간·진단 조회에 대해서는 이 문서가004 §3–5의100ms샘플/1600ms상한과006 O13/O15/O27의 시간 기대값을 대체한다.** 나머지 계약은004를 참조한다. 새 계보 예산은 L2 최대2회, 구현 L4 최대2회(각 최초검토+수정 재확인)이며 별도로 센다. 새 미해결 지적을 통과로 간주하지 않는다.

이번 구현 단위는 장치 독립 C++17 CAN codec와 정지 조정기, 가짜 transport/시계의 호스트 시험, ESP-IDF 프로젝트의 **통신 미연결 준비 골격**이다. 전체 운전 supervisor·실제 TWAI·Wi-Fi/웹 서버·플래시·모터 제어는 이번 검증된 코어로 후속 연결한다. 웹 시안은 계속 모의 상태다. 실제 송신 adapter가 없는 준비 단계에서도 부품 없이 확인할 수 있는 오류·시간 처리 코드는 실행한다.

외부 Sonnet 정식 bridge 파일의 읽기가 로컬 Python lint hook(기존 hard-coded absolute path)에서 거절됐다. 중앙 도구를 수정하거나 우회하지 않는다. 이번 L2/L4는 작성자와 분리한 동일 계열 검토로 진행하며 외부 계열 부재를 잔여 리스크로 기록한다. 외부 재가용 시 실제 보드 통합 전 검증 전제를 재검토한다. 이는 실물 운전 허가가 아니다.

## 1. 원인과 선택

1300ms 무송신 감시 뒤 같은코드200ms 간격으로 위치3샘플을 받으려면 낙관적 최소1700ms다. 이전 episode1600ms 상한과 양립하지 않는다. 100ms 위치 샘플 조건도 응답지연+RX서비스+격리130ms를 넘겨야 한다는 조건에 어긋난다.

전체 상한만 늘리거나100ms를 유지하는 대신 **송신 준비 → 무송신 감시 → 정지 진단** 세 단계를 구분한다. 정지 명령은 앞 단계에서 즉시 시도하며 늘어나는 시간은 정지 여부를 읽는 시간이다. 이 시간은 기계적 정지시간 보장이 아니다.

## 2. 단조 시계와 단계별 계약

모든 시각은 uint64 밀리초, 외부에서 주입된 단조 시계다. 시간 역행·덧셈 overflow는 Fault다. `now >= deadline`이면 만료이며 시각 경계의 성공 이벤트보다 먼저 처리한다. 반복 stop은 기존episode에 병합하고 시작시각·epoch·F7시도·기한을 바꾸지 않는다. terminal 상태에서는 재시작하지 않고 새cycle 생성은 후속 supervisor의 명시적 재점검 책임이다.

| 단계 | 기한/조건 | 출력 |
|---|---|---|
| Isolating | 최초stop T0+100ms 미만 | 기존 송신·큐·알림 격리 요청. 완료보고가 없거나 실패하면Fault |
| StopCommands | T0+600ms 미만 | active_axes 순서대로F7 각최대1회. TX완료50ms, F7성공ACK200ms 기한. TX/ACK 미확인 시Fault |
| Quiet | 마지막확인TX+1300ms까지 | 모든조회/설정/keepalive 금지, 수신은상태승격없이기록 |
| Verifying | 진입V+1700ms 미만 | 아래3회전 고정진단. 매축3개위치+최종F1/32/3A 평가 |
| 전역 상한 | T0+3600ms 미만 | 모든단계를포함. 반복사건으로연장없음 |

격리 성공·heartbeat1000ms 설정/readback 확인·프로필의지연상한 승인·정지 오차값이 모두 명시되어야 자동Quiet/Verifying이 가능하다. 하나라도 미확정이면Fault로 보내며 정지 성공이라고 표시하지 않는다. 실제 물리 차단은 이 코어가 제어/감지하지 않는다.

F7는 CAN TX 성공과 MKS 성공응답을 구분한다. 송신 API 접수만으로 TX성공보고를 만들지 않는다. ACK가 TX완료 이벤트보다 먼저 들어오면 raw기록만 하고성공승격하지않는 보수 정책이다. 실제adapter에서이벤트순서를정합화해야하며미확인으로안전하게실패할수있다. 이미 전송된FD를취소했다고주장하지않는다. bus-off/격리실패는 새TX출력없이Fault다.

## 3. 진단 조회 스케줄과 수용창

N은1또는2, active_axes는[1]/[2]/[1,2]만 허용한다. 코드순서 `[31,F1,32,3A]`, 각코드안에서active_axes순서로 총4N슬롯을만들고 **3회전만** 반복한다. 슬롯 시작은 V+k×60ms다. sender는명목시각부터10ms미만에실행해야하며놓친슬롯을나중에몰아서전송하지않는다. 이미inflight가남아있으면Fault다. TX는50ms미만에완료해야하므로다음60ms슬롯전완료가능하다.

TX완료부터 응답Rmax100ms+RX서비스10ms의 **110ms미만**을 읽기수용기한으로 한다. adapter가dequeue즉시찍은RX시각과supervisor현재시각을구분하며RX서비스/처리지연10ms이상·RXoverflow는Fault다. 코어의frame입력은실제CAN바이트이고 요청nonce/epoch를프레임에만들어붙이지않는다. pending은축·코드별1개,다른코드pending은겹칠수있고최대8개로고정한다.

§2의기한우선규칙에따라처리시각now도수용기한미만이어야한다. dequeue가109ms여도처리가110ms이면거절한다. 최악수용fixture는TX49ms/RX109ms/처리지연0ms,별도서비스fixture는RX99ms/처리지연9ms로구분한다. 처리지연을더해기한을연장하지않는다.

같은축·코드의다음요청명목간격은 N×4×60ms = **1축240ms / 2축480ms**. 이전요청이최대10ms늦게시작하고50ms동안TX대기했더라도 실제TX사이간격은180ms이상으로130ms격리하한을넘는다. 추가로 새요청시각이이전TX완료+130ms이하이면전송하지않고Fault다. 위치샘플간격을100ms로강제하는이전문구는적용하지않는다.

L4 R1의action소비지연반례를반영해 `take_action(now,out)`도시계를받아기한만료를우선검사한다. 진단action은명목slot+10ms이후출고할수없으며TX기한은action생성부터50ms로유지한다. action의dispatch_before를adapter에도전달하고즉시제출·지연큐/재전송금지를연결계약으로둔다. 실제adapter는이번단위에없으므로선로상의제출검증은후속통합시험대상이다.

2축의최종슬롯k23은V+1380ms, 슬롯지연<10+TX<50+응답서비스<110을합해마지막응답은 **V+1550ms미만**이다. 1축최종k11은V+660ms로V+830ms미만이다. 따라서진단1700ms안에여유를두고수용가능하다. 전역3600ms = 준비600+Quiet1300+진단1700이며단계별미만조건으로경계와충돌하지않는다.

진단의정지관측은각축의이번진단에서만얻은signed48 위치3개가설정된tolerance_counts안에서안정(min/max차이),최종F1=1,속도32=0,3A가0또는1의유효값이며최종관측들이유효해야한다. 정지확인은토크해제확인이아니므로enable=1도STOPPED_RECHECK대상이다. 이후토크해제는004의별도유지보수경로다.

마지막회전의4개관측은완료판정시 **각700ms미만**이어야한다. 이값은2축마지막회전에서가장이른위치TX(V+960)부터최종수용(V+1550미만)까지590ms미만에대한여유이며,정지진단에만적용한다.004의정상운전400ms stale값을무작정확장하지않는다. 앞선2개위치샘플은안정성추세의이력이고현재상태값으로표시하지않는다. 이조회창의기계적타당성은실물검증전승인되지않으며production프로필은기본미승인이다.

F1또는속도가회전중어느샘플에서든움직임을나타내거나위치3샘플범위가오차를넘으면Fault다. 관측이빠짐/중복/기한경계/잘못된ID·DLC·checksum/기준밖code이면유효관측을갱신하지않는다. pending을소비한중복프레임은무시하며timeout이면Fault다. CAN에nonce가없어임의지연replay를구분하지못하는한계는그대로다. bootstrap과실물응답상한승인전에는실모터운전으로사용하지않는다.

## 4. 첫 구현 구조

`src/firmware/`에target프로젝트를분리한다. 장치독립코드는`components/robot_core/`이며외부라이브러리·동적할당·네트워크·파일·시리얼API를호출하지않는다.

- codec: 표준ID1/2·DLC/flags·checksum검사,31signed48/32signed16/F1/3A/F3/F7/FD응답,read·F3·F7·고정FD100p명령인코딩. 미지원코드는명시적거절.버전응답모순을추정해파싱하지않는다.
- StopCoordinator: Idle/Isolating/StopCommands/Quiet/Verifying/StoppedRecheck/Fault. 외부단조시각·TX결과·rawRX·격리결과를입력받고 bounded action(격리요청/송신/상태변화)을낸다. 새운전허가/FD송신은이정지모듈의기능이아니다.
- transport계약: action의로컬토큰으로TX완료를상관시킴(선로nonce아님). 옛토큰/세대/unknown결과는성공으로변환하지않음. 하나의inflight,4N읽기pending,episode최대2개의F7.
- ESP-IDF v5.5.6 CMake/Kconfig 골격: 기본값실물프로필미승인, app_main은준비상태만기록. TWAI/Wi-Fi/모터동작을시작하지않음. 이골격은target빌드가실행되기전까지NOT_RUN이다.
- tests/host: 실제production codec/StopCoordinator를Windows C++컴파일러로빌드해실행. 가짜시계/transport로1축2축정상최악지연·경계·반복stop·오염프레임·TX실패검증. Python모형의성공을C++실행으로대신표시하지않는다.
