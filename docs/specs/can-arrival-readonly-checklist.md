# CAN 모듈 수령 준비·읽기 전용 시험 체크리스트

작성 2026-10-30 · 대상: Waveshare ESP32-S3-RS485-CAN-U + MKS SERVO42D CAN MT 두 세트.
**현재 상태: 문서/코드 대조 완료, 실물 단계는 전부 NOT_RUN.** Isaac 노트북은 필요 없다. 이후 USB 인식·로그 확인에는 현재 Windows PC를 사용할 수 있다. PC도 사용하지 않을 때는 수령품 확인·무전원 작업까지만 진행한다.

보유40mm NEMA17 두 대는 사용자 보고 기준 J2/J3 시험용이다. 이 목록은 최종6축의 큰 모터 선정·감속기·그리퍼 검증을 포함하지 않는다. 다음 주 도착 예상은 사용자 보고이며 확정 배송일은 아니다.

## 1. 지금 준비할 것

- [ ] 모터/드라이브를 A·B로 구분하고 라벨·CAN 단자·정격·HW/FW 사진을 모은다. 미확인 값은 빈칸으로 남긴다.
- [ ] 데이터 전송 가능한 USB-C 케이블, 멀티미터, 절연 도구, 케이블 표시, 고정 브래킷을 모은다. 보유 여부를 먼저 확인하며 추가 구매는 실행하지 않는다.
- [ ] 통신선과 전원선을 별도로 표시한다. 통신 후보는 RVSP4core24AWG, 모터 급전선은 별도18AWG 두 선이다. 실제 주문/수령 상태를 기록한다.
- [ ] 통신선의 실제 꼬임쌍을 확인한다. 색만 보고 두 심을 선택하지 않는다. RVSP 사진/상품명만으로120Ω 특성 임피던스가 확인된 것은 아니다.
- [ ] CAN선 전체 배치는 처음에 가능한 짧은 고정 벤치로 정한다. 모터선/전원선과 묶지 않고 단자 근처까지 꼬임을 유지한다.
- [ ] 모터 축에는 링크·감속기·풀리·하중을 달지 않는다. 모터 고정은 실물 나사 깊이와 체결 길이를 확인한다.
- [ ] 결과 사진/로그를 모을 폴더와 아래 기록표를 준비한다. 빈 결과를 PASS로 미리 채우지 않는다.

## 2. 모듈 수령 당일: 식별 → 무전원 확인

| 순서 | 할 일 | 통과 조건 / 기록 | 중단 조건 |
|---|---|---|---|
| B01 | 모듈·안테나·단자·기판 리비전 사진 | 실제 CAN-U 모델과 CAN H/L 표시 확인 | 다른 모델/RS485 전용/단자 불명 |
| B02 | A/B 라벨·HW/FW·CAN 옵션 대조 | 실물과 해당 매뉴얼 버전 연결 | 버전·단자 설명 불일치 |
| B03 | 전원과 USB 모두 분리하고 잔류 전압 확인 | 저항 측정 전에 무전압 | 전압이 남거나 계측 상태 불명 |
| B04 | 케이블 도통·H/L 교차·전원선 혼입 점검 | H→H, L→L, 같은 꼬임쌍, H/L 단락 없음 | 교차·피복 손상·단락 |
| B05 | 실제 CAN 종단 점퍼 식별 | CAN용과 RS485용을 구분하고 사진 기록 | 실물 표시와 회로 불일치 |
| B06 | 조립한 무전원 버스의 H–L 저항 측정 | 양 끝120Ω일 때 약60Ω, 측정값 기록 | 예상과 다르면 급전하지 않고 점퍼/배선 재확인 |

약60Ω은 종단 대조의 단서이며 통신·배선 전체 합격 증명이 아니다. 약120Ω은 종단 하나, 약40Ω은 종단 셋의 가능성을 먼저 확인하되 측정값만으로 원인을 단정하지 않는다. 전원이 들어온 상태에서 저항을 재지 않는다. [종단 근거: Kvaser](https://kvaser.com/developer-blog/how-to-test-your-can-termination-works-correctly/).

### 수령품 표시를 따라 만드는 H/L 배치

```text
A 한 대:     Waveshare H/L [종단ON] ─── A H/L [종단ON]
B 한 대:     Waveshare H/L [종단ON] ─── B H/L [종단ON]
A+B 두 대:   Waveshare H/L [종단ON] ─── A H/L [종단OFF] ─── B H/L [종단ON]
```

배치를 바꾸거나 B로 교체할 때마다 전체 전원/USB를 끄고 잔류 전압을 확인한다. 통전 중 배선/점퍼/모터 커넥터를 바꾸지 않는다. 중간 접속은 단자가 허용하는 도체 수와 맞는 접속 방식으로 만들고 두 선을 임의로 한 구멍에 밀어 넣지 않는다.

**이 Waveshare의 외부 CAN 단자는 H/L이다.** 남는 두 심과 차폐는 초기 벤치에서 각각 절연해 둔다. SH1.0 GND·전원−·MKS COM·EGND를 임의의 CAN 기준선으로 연결하지 않는다. 보존된 회로는 CAN측 SGND와 MCU측 GND를 구분한다. MKS A/B의 전원 GND 귀환은 CAN 기준선과 별개로 전원 배선에서 처리한다. 다른 보드/리비전이라면 이 배치를 적용하기 전에 다시 대조한다. [Waveshare 인터페이스](https://docs.waveshare.com/ESP32-S3-RS485-CAN), 로컬 회로 근거 `.dev/can-evidence/wiring/waveshare-schematic.txt`.

## 3. 보드 단독 확인 — 드라이브는 연결하지 않음

- [ ] CAN H/L·드라이브 전원·외부DC를 모두 분리한 상태에서 보드만 USB로 연결한다. USB와 외부DC를 동시에 급전하지 않는다.
- [ ] Windows 장치 관리자에서 실제 장치/포트·장치ID·케이블 연결 전후 차이를 기록한다. 포트 이름을 미리 고정하지 않는다.
- [ ] 장치가 안 보이면 먼저 데이터 케이블·USB 포트를 확인한다. 인식 실패를 CAN 불량으로 처리하지 않는다.
- [ ] 기존 펌웨어 식별이 가능하면 로그/버전을 저장한다. 식별 불가·로그 없음은 그대로 기록한다. 제조사 예제를 무심코 실행하거나 펌웨어를 플래시하지 않는다.
- [ ] CAN LED 점등·USB 인식만으로 CAN 송수신 PASS를 표시하지 않는다. 보드 단독 시험에는 정상 응답할 MKS 노드가 없다.

공식 문서는 USB5V와 별도 DC입력7~36V를 구분한다. 이 값은 보드 사양이며 MKS 전원 설정값이 아니다. MKS가 섞인 공통 전원을32V로 설정하지 않는다. 실제 드라이브 전원은 실물 정격과 기존 전원 점검표를 대조한다. [Waveshare 사양](https://docs.waveshare.com/ESP32-S3-RS485-CAN).

## 4. 실제 CAN 읽기 전에 반드시 확인할 실행 조건

현재 `app_main.cpp`는 하드웨어 승인false이며 기본 CAN/네트워크 비활성이다. 준비 실행부도 실물 통신용으로 승인된 읽기 전용 이미지가 아니다. **따라서 지금은 위1~3단계 준비와 아래 시험 설계까지 완료한 상태다.** 보드가 도착했다는 이유로 승인false를 바꾸거나 기존 유지보수/운전 경로를 실행하지 않는다.

- [ ] 도착품 HW/FW·단자·전원·bitrate·현재 CAN ID가 확인됐다. 코드 후보는 S3 TX15/RX16·500kbit/s지만 현품 확인 전 확정값이 아니다.
- [ ] 전원 시 자동 홈/제로/enable·보정 요구·출고 펌웨어 동작을 검토했다. **움직임을 허용할 수 없고 자동 동작을 배제할 수 없으면 드라이브에 전원을 넣지 않고 여기서 보류한다.** CAN 읽기 명령도 전원 투입에 따른 동작을 막아 주지 않는다.
- [ ] 실제 송신 실행부가 아래 읽기4종·확인한 단일 ID만 보낼 수 있음이 별도 검토됐다. UI 미표시가 아니라 송신 경계의 허용 목록, 시작 시 무송신, 자동 설정/복구/재시도 없음, 원 TX/RX 기록을 확인한다.
- [ ] 기존 이미지로 대체하지 않았다. `robot_boot/supervisor.cpp`의 유지보수에는 F3·heartbeat 설정 쓰기 경로가 있어 읽기 전용 도구로 간주할 수 없다.
- [ ] 시험 전에 별도 읽기 전용 실행부의 구현·장치 시험 조건을 확정한다. 이번 문서 작성은 그 구현·플래시·실물 전원/송신을 수행한 것으로 처리하지 않는다.

## 5. 조건 충족 후 시험 순서 — A → B → A+B

아래는 나중에 위 조건을 충족한 뒤 사용할 순서다. 기본 ID가 겹칠 수 있으므로 처음부터 두 드라이브를 동시에 연결하지 않는다.

1. **A만 연결:** B는 전원/CAN 모두 분리한다. A의 실제 ID가 현재 지원하는1/2인지 확인한다. ID 불명 시 broadcast·전체 ID 스캔·임의 ID 변경을 하지 않고 보류한다.
2. **상태부터 읽기:** enable(3A) → 운전 상태(F1) → 위치(31) → 속도(32)를 한 명령씩 보내고 해당 응답을 확인한 뒤 다음으로 간다. burst/자동 반복은 하지 않는다. 응답 제한시간과 명령 간격은 검토된 읽기 실행부가 정한 값을 기록하며 도착 당일 결과에 맞춰 늘리지 않는다.
3. **응답 대조:** CAN 표준 데이터 프레임, 실제 ID, DLC, 첫 바이트 opcode, checksum, 오류 counter·bus 상태를 함께 기록한다. 송신 접수와 실제 TX 완료, 응답 수신을 구분한다. 응답 없으면 그대로 NO_RESPONSE로 남기며 자동 재전송하지 않는다.
4. **중단 판정:** enable=1, F1=0(조회 실패), F1=2~6(운전/홈/보정 상태), 예상 밖 움직임·진동·이상·보정 요구·bus-off·잘못된 응답이면 다음 단계로 넘어가지 않는다. 예상 밖 물리 동작이면 접근하지 않고 준비된 전원 차단 수단을 사용한다. F3 해제나 F7 명령을 즉석 대안으로 추가하지 않는다.
5. **B 개별 반복:** 전원/USB OFF·잔류 전압 해소 후 A를 분리하고 B만 같은 순서로 확인한다. B도 ID1이면 개별 기록은 남길 수 있으나 A+B 동시 연결은 보류한다.
6. **A+B 동시 읽기:** A/B의 ID가 서로 다르고 각각1/2이며 개별 확인을 모두 통과했을 때만 두 노드를 선형으로 연결한다. 무전원 종단 검사를 다시 하고 두 ID를 차례로 조회한다. 현 단계에서 ID 설정 명령은 보내지 않는다.
7. **종료:** 로그·전압/전류 표시·배선/종단 사진을 저장하고 송신을 종료한 뒤 전원을 끈다. 결과는 ‘읽기 전용 통신 확인’ 범위로만 남긴다.

F1은 매뉴얼상 SR_OPEN/SR_CLOSE/SR_vFOC 모드에서 유효하다. 모드 불일치·CAL 요구·펌웨어 불일치가 보이면 모드를 바꾸거나 보정해서 통과시키지 않는다. 31의 위치값은 원시 encoder 누적값이며 이번에는 영점·실제 관절각·회전 방향으로 보정/변환하지 않는다. 속도0/enable0/정지 상태 응답만으로 물리 안전 정지·무토크·시간 성능을 입증하지 않는다.

## 6. 읽기 전용 프레임 대조표 — 아직 송신하지 않음

Classical CAN, 표준11bit ID, DATA frame, RTR=false, EXT=false. 각 TX의 DLC는2이며 마지막 바이트는 `(CAN ID + 앞선 데이터 바이트 합) & 0xFF`다. `0xFD` 명령과 CAN FD 프레임은 다른 개념이다. 이 시험에서는 둘 다 사용하지 않는다.

| 조회 | CAN ID | TX DATA(hex) | RX DLC | 응답값 기록 |
|---|---|---|---|---|
| enable | 0x001 | 3A 3B | 3 | 0=disabled, 1=enabled |
| 운전 상태 | 0x001 | F1 F2 | 3 | 0=조회실패, 1=stop, 2~6=운전/홈/보정 |
| 누적 위치 | 0x001 | 31 32 | 8 | signed48, big-endian 원시값 |
| 속도 | 0x001 | 32 33 | 4 | signed16, big-endian, rpm |
| enable | 0x002 | 3A 3C | 3 | 동일 |
| 운전 상태 | 0x002 | F1 F3 | 3 | 동일 |
| 누적 위치 | 0x002 | 31 33 | 8 | 동일 |
| 속도 | 0x002 | 32 34 | 4 | 동일 |

허용 여부는 **명령 첫 바이트**로 구분한다. 예를 들어 `F1 F3`에서 F3은 checksum이지 토크 명령이 아니다. 표는 현재 `mks_codec.cpp/.hpp`와 `tests/host/test_codec.cpp`의 고정 프레임, Makerbase CAN V1.0.9 p25·27·29·70을 대조했다. 실제 수령 FW가 이 문서 버전과 같다고 가정하지 않는다.

## 7. 현장 기록표

| 항목 | A | B | A+B |
|---|---|---|---|
| 실시 날짜/작업자 | 미실시 | 미실시 | 미실시 |
| 모델/HW/FW/사진 경로 | 미확인 | 미확인 | — |
| 실제 ID/bitrate/모드 | 미확인 | 미확인 | 서로 다른 ID 확인 전 보류 |
| 종단 점퍼/무전원 H–L Ω | 미측정 | 미측정 | 미측정 |
| 사용 실행부 버전/해시·허용목록 검토 | PENDING | PENDING | PENDING |
| 전원 V/A·전원 전/후 상태 | 미측정 | 미측정 | 미측정 |
| 3A / F1 / 31 / 32 결과 | NOT_RUN | NOT_RUN | NOT_RUN |
| TX완료/원 RX/오류 counter 로그 | 없음 | 없음 | 없음 |
| 결과·중단 이유 | NOT_RUN | NOT_RUN | NOT_RUN |

원 로그에는 세션/장치, 명령 전후 단조시각, ID·DLC·DATA·flags, 송신 접수/완료, RX dequeue 시각과 그 시각의 의미, 원 응답·파싱값·에러·중단 이유를 남긴다. dequeue 시각을 선로 도착 하드웨어 시각으로 표시하지 않는다. 상태는 PASS_READONLY / NO_RESPONSE / INVALID_FRAME / QUERY_FAILED / CAL_REQUIRED / BLOCKED / NOT_RUN으로 구분하고 재시도 전 원 실패를 보존한다.

## 8. 이번에 하지 않는 것과 다음 단계

보정(CAL), 영점/홈 복귀, 설정 쓰기(ID/bitrate/모드/heartbeat 포함), F3 토크 변경, F7, 위치·속도 이동, 정상 운전 인계, 정지 성능·축 방향·하중 시험, 펌웨어 플래시·업데이트는 실행하지 않는다. 기본 승인false와 장치 비활성 상태를 유지한다. 현재 벤치 코드의 지원 ID는1/2이며 최종6축·그리퍼 지원 완료 판정이 아니다.

다음 준비 작업은 **실물 정보를 입력으로 받는 전용 읽기 진단 실행부 설계**다. 이후 원자료/시간/오류 처리 HOST 대조와 실제 하드웨어 시험을 구분한다. 이번 문서 작업에서는 기존 시험 횟수 원장을 재사용하거나 Isaac 노트북에 재접속하지 않았다.
